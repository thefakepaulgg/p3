# Background shell precedents

## Answer

**Yes—including real, reusable Pi extensions that override `bash`, automatically yield long commands, and wake the agent on completion.** The closest match is **`pi-patty-bg-tasks`**; **`@aliou/pi-processes` plus its optional bash override example** provides another implementation. This is not just an async terminal UI pattern.

Online primary-source inspection on 2026-10-15; repository citations below pin the observed revisions. No packages installed, candidate commands executed, runtime tests run, or configuration changed. Native web search was unavailable for this model; discovery used GitHub CLI search/API and official documentation read through the native browser. The earlier [local analysis](bash-auto-background-tool.md) supplies p3 integration context, not online evidence.

## Six strongest precedents

### 1. Pi: `pi-patty-bg-tasks` — closest complete match

The [package manifest](https://github.com/patty-io/pi-patty-bg-tasks/blob/697010eaa88ca1b861fce554a149a5f019a7439a/package.json) identifies version 2.0.0, MIT license, Pi extension entry point, and `@earendil-works` peers. Its [README](https://github.com/patty-io/pi-patty-bg-tasks/blob/697010eaa88ca1b861fce554a149a5f019a7439a/README.md) documents `pi install npm:pi-patty-bg-tasks` (not run).

- **Automatic threshold:** [the actual `bash` override](https://github.com/patty-io/pi-patty-bg-tasks/blob/697010eaa88ca1b861fce554a149a5f019a7439a/src/tools/bash.ts) races process completion against a timer/manual background request. Default is **120 seconds**; `bash({command, timeout: 10})` selects ten seconds before promotion, not a normal kill deadline for eligible commands. `run_in_background: true` and separate `bash_bg` skip the foreground wait. A two-second quick-completion race precedes the main race; it is **not** the auto-background threshold.
- **Real handoff:** the same spawned process continues; the early result contains a task ID and log path, not a completed-command verdict. Output goes directly to a file descriptor. The timer does not auto-background in the package's noninteractive mode; sleep-related guards also make behavior nonuniform.
- **Wake, not polling:** [notification code](https://github.com/patty-io/pi-patty-bg-tasks/blob/697010eaa88ca1b861fce554a149a5f019a7439a/src/notify.ts) sends individual `<task-notification>` custom messages; [delivery constants](https://github.com/patty-io/pi-patty-bg-tasks/blob/697010eaa88ca1b861fce554a149a5f019a7439a/src/types.ts) set `deliverAs: "steer", triggerTurn: true`. Reads/attach/kill can suppress an already-consumed completion notification. Its pre-send latch prevents duplicate sends but means a failed send is not retried—not durable exactly-once delivery.
- **Control/dependencies:** `jobs` supports output, kill and attach-to-wait. Genuine foreground cancellation kills the process group; a requested background handoff deliberately survives the turn abort. README says any session shutdown kills running jobs; logs remain in `/tmp/pi-bg`. Dependent work must attach/wait, not treat the initial acknowledgement as success.

A real [fork](https://github.com/tomkhoailang/pi-patty-bg-tasks/blob/ccf426c58b8b8acb681fe62ab3ab47e6c29c4676/src/types.ts) defaults to **15 seconds**, configurable with `PI_PATTY_BG_TIMEOUT_MS` (therefore 10000 is expressible). This verifies the fork's threshold, **not** its comment's claim about Claude Code internals or npm publication. Main package per-call `timeout: 10` already expresses the requested window.

### 2. Pi: `@aliou/pi-processes` — separate manager plus optional override

The [manifest](https://github.com/aliou/pi-processes/blob/434fa0a860b1fa4fe9fccdc986964d865ef98e47/package.json) identifies version 0.13.2, MIT, and `@earendil-works` peers. [README](https://github.com/aliou/pi-processes/blob/434fa0a860b1fa4fe9fccdc986964d865ef98e47/README.md) documents `pi install npm:@aliou/pi-processes` (not run), macOS/Linux support, `/ps`, logs, kill, and stdin writes.

- **Default surface:** explicit `process` start/list/output/stop/write/update/clear actions; installing the package alone does **not** automatically yield every `bash` call.
- **Actual automatic override:** [`examples/bash-background.ts`](https://github.com/aliou/pi-processes/blob/434fa0a860b1fa4fe9fccdc986964d865ef98e47/examples/bash-background.ts) registers `bash`, spawns once, and hands the live child plus captured stdout/stderr to the manager's synchronous `processes:command:adopt` channel. It yields after **120 seconds without a timeout**, at an explicit `timeout` in seconds, or with Ctrl+Shift+B. Thus `timeout: 10` gives the desired foreground window. Failed adoption at an explicit timeout kills the child; failed automatic/manual adoption leaves foreground execution intact.
- **Packaging detail:** that example is a separate copy/adapt step; `examples` is absent from the manifest's npm `files` list. Do not assume npm installation enables or includes it.
- **Event-driven wake:** [notification documentation](https://github.com/aliou/pi-processes/blob/434fa0a860b1fa4fe9fccdc986964d865ef98e47/docs/notifications.md) specifies success/failure default to `turn`, killed to `context`, plus readiness/error log watches. [The delivery handler](https://github.com/aliou/pi-processes/blob/434fa0a860b1fa4fe9fccdc986964d865ef98e47/extensions/processes/handlers/notifications.ts) steers busy runs; when idle it persists the notification without triggering a turn, then coalesces a `sendUserMessage("")` wake. This is deliberate host integration, not polling.

Important real integration report: [issue #121](https://github.com/aliou/pi-processes/issues/121) describes idle `triggerTurn` bypassing `before_agent_start`, losing prompt extensions/breaking a bridge. The inspected implementation contains its idle-wake workaround. Verify the installed Pi version rather than blindly copying notification flags.

### 3. Pi: `pi-interactive-shell` — immediate async dispatch, not threshold yielding

[README at the inspected revision](https://github.com/nicobailon/pi-interactive-shell/blob/f6308e627c7b0eaa07598fda4059fa78818ebdf6/README.md) documents the actual package and separate `interactive_shell` tool. `mode: "dispatch", background: true` returns a stable session ID immediately and uses `triggerTurn` completion notifications with an output tail; input/status/attach/kill operate on that ID. Hands-free mode instead uses queries and quiet updates. This establishes a separate-tool precedent, **not** automatic promotion of ordinary bash after ten seconds.

Its dispatch default includes auto-close on quiet (15-second startup grace, then eight seconds of silence). Documentation explicitly says `completionReason: "auto-close-quiet"` is **not a command verdict**, and cancellation/termination is best-effort. Disable quiet auto-close when natural exit is the required completion signal. README says reload preserves sessions, but quitting/switching sessions terminates them.

### 4. Claude Code — native Bash auto-backgrounding

Official [tools reference](https://code.claude.com/docs/en/tools-reference#foreground-commands-that-move-to-the-background) explicitly says foreground commands reaching their timeout move to the background rather than stop, except commands starting with `sleep`. Default foreground timeout is **two minutes**, configured through `BASH_DEFAULT_TIMEOUT_MS`; Claude can pass per-call `timeout`. The result states the timeout-triggered move, task ID and output path. Directory changes in a moved command do **not** carry over to subsequent commands.

[Interactive-mode documentation](https://code.claude.com/docs/en/interactive-mode#background-bash-commands) also documents explicit background requests and Ctrl+B, file-backed output, `/tasks`, and cleanup at exit. Disabling background tasks or using bare mode restores timeout-as-stop behavior. Current tools docs distinguish local interactive background jobs (no runtime limit) from unattended jobs (separate background limits). Thus foreground yield and eventual kill deadline are distinct lifecycle concerns.

This is a built-in **completed-or-backgrounded Bash contract**, not proof that an existing completion-only API can be wrapped transparently. The inspected sections establish the automatic handoff; they do not establish a universal ten-/15-second default or the exact idle completion-wake scheduling. Pi packages' claims of “Claude Code parity” are not independent evidence for those internals.

### 5. Codex — native ten-second yield plus resumable process handle

At [revision 34420d4](https://github.com/openai/codex/blob/34420d42648f627f766bd347532dcaad5475a68b/codex-rs/core/src/tools/handlers/unified_exec.rs), `exec_command` defaults `yield_time_ms` to **10,000**; `write_stdin` takes `session_id`, `chars` and its own yield window. [Process-manager code](https://github.com/openai/codex/blob/34420d42648f627f766bd347532dcaad5475a68b/codex-rs/core/src/unified_exec/process_manager.rs) returns a process handle while running and an exit code when finished. [The handler](https://github.com/openai/codex/blob/34420d42648f627f766bd347532dcaad5475a68b/codex-rs/core/src/tools/handlers/unified_exec/write_stdin.rs) explicitly calls empty writes background polls. This is the closest **API** precedent for the requested foreground window: execution yields rather than times out.

Do not conflate that with wake-on-completion: [the exit watcher](https://github.com/openai/codex/blob/34420d42648f627f766bd347532dcaad5475a68b/codex-rs/core/src/unified_exec/async_watcher.rs) emits `ExecCommandEnd`, but that alone does not establish a new model turn. [Open issue #50079](https://github.com/openai/codex/issues/50079) specifically requests automatic continuation after background CLI exit; it is user-reported evidence, not a controlled reproduction here. Also, [the current one-shot variant](https://github.com/openai/codex/blob/34420d42648f627f766bd347532dcaad5475a68b/codex-rs/core/src/tools/handlers/unified_exec/exec_command.rs) removes yielding/session IDs and terminates on timeout/cancel. Not every Codex execution configuration has the resumable contract.

### 6. OpenCode V2 — explicit/manual shell jobs with automatic continuation

[Shell plugin source](https://github.com/anomalyco/opencode/blob/582c974ee362683f5dd5c7f9741cae207581c6b5/packages/core/src/tool/plugin/shell.ts) accepts `background: true`, returning `status: "running"`, `shellID` and output-file path immediately. Foreground execution uses `jobs.block`; a user-backgrounded result disables the shell timeout and forks a notifier that waits for completion and posts `sessions.synthetic(...)`. The model instruction explicitly says **do not poll**, do independent work, or end the response and be resumed automatically.

This is **not an observed automatic elapsed-time threshold**: foreground timeout defaults to two minutes and produces an exceeded-timeout result; explicit background commands default to no timeout. [Job source](https://github.com/anomalyco/opencode/blob/582c974ee362683f5dd5c7f9741cae207581c6b5/packages/core/src/job.ts) exposes start/block/background/cancel/wait and durable notification markers for recoverable jobs—not a guarantee arbitrary OS processes survive restart. [Issue #54221](https://github.com/anomalyco/opencode/issues/54221) documents V2's shell/subagent-only backgrounding and proposes extending it to execute/MCP/plugin calls, including an **opt-in automatic threshold**. That proposal is not an implemented feature claim.

## Implications for p3

- **Override is a real ecosystem path, not unsupported API trickery.** Pi's [official override example](https://github.com/earendil-works/pi/blob/698a2d23b86a5045dd54554354a5e0cb7e466795/packages/coding-agent/examples/extensions/tool-override.ts) explicitly supports same-name replacements. In [Pi issue #4850](https://github.com/earendil-works/pi/issues/4850#issuecomment-4511596031), maintainer badlogic responds to the need for a full bash override: “this is the way,” and says Pi will not support it out of the box. The proposed `BashProcessHandle` API in that issue is not evidence of a merged core facility.
- If the requirement is **every existing bash call automatically yields**, `pi-patty-bg-tasks` demonstrates that exact choice, with a ten-second per-call window available. If preserving existing `await bash()` completion semantics matters, a separate tool remains a valid migration choice; `process` and `interactive_shell` demonstrate it. Online precedent removes the argument that an override is unusual, **not** the contract tradeoff identified in the earlier note.
- All yielding variants return a **running acknowledgement**, not a final success. Dependent commands need a wait/attach operation or must remain in the same shell command (`build && next-step`); completion notification cannot retroactively finish an already-resolved promise. New schemas/instructions should make this state explicit, as OpenCode does.
- Reuse candidates still require p3-specific evaluation: existing sandbox/backend overrides, codemode output shape, cancellation after handoff, session shutdown, completion redaction and idle wake hooks. The Pi overrides inspected spawn their own children; they do not transparently inherit an arbitrary existing execution backend. No runtime compatibility with this installed p3/Pi combination was proved.

**Evidence gaps:** no verified relevant package named simply `pi-shell` was found (search hits included unrelated shells); no implementation claim is based on that name. `pi-tian-background-terminals` appeared in pi-processes' related-package list, but its source was not independently located/inspected, so it is not counted as a verified precedent. Published npm contents/versions were not downloaded or independently checked; package existence/install surfaces above are repository manifest/README evidence. Official docs are live, unpinned pages; source inspection is not a runtime reliability assessment.
